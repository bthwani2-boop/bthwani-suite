# BThwani DSH — خطة وأوامر تنفيذ إغلاق منطق توصيل المتجر وشاشة طلبات الشريك

> نوع الوثيقة: Master Execution Plan + VS Code Copilot Commands
> النطاق: DSH كمنظومة واحدة متعددة الأسطح
> المسار المحلي المعتمد: `C:\bthwani-suite`
> الريبو المعتمد: `bthwani2-boop/bthwani-suite`
> قاعدة التنفيذ: لا يوجد منع أعمى لأي سطح، ولا يوجد تعديل عشوائي خارج خريطة الأثر
> الهدف: إغلاق منطق الطلبات وتوصيل المتجر والشريط السفلي وبطاقة الطلب عبر التطبيقات الأربعة ولوحة التحكم وWLT بدون فجوات أو تناقضات

---

## 0) القرار النهائي الملزم

### 0.1 لا يظهر اسم العميل في بطاقة الطلب مطلقًا

من الآن فصاعدًا داخل شاشة طلبات الشريك DSH:

```text
اسم العميل لا يظهر في بطاقة الطلب.
اسم العميل لا يظهر في Header البطاقة.
اسم العميل لا يظهر كـ meta داخل البطاقة.
اسم العميل لا يظهر في البلوك المنسدل إلا إذا كان هناك احتياج قانوني/تشغيلي مثبت لاحقًا.
```

البديل العملي داخل البطاقة:

```text
رقم الطلب
حالة الطلب
الإجراء الآن
الوقت/SLA
تفاصيل العناصر
المبلغ
الدفع
نمط التوصيل
الجهة التالية
ملاحظات الطلب
جرس الطلب الجديد
```

السبب: شاشة الشريك قد تكون مع الكاشير داخل متجر مزدحم. الكاشير يحتاج تشغيل الطلب لا قراءة ملف العميل.

---

### 0.2 كل تفاصيل الطلب المهمة تظهر داخل بطاقة الطلب نفسها

بطاقة الطلب هي مركز القرار للكاشير. لا يجوز أن تكون البطاقة فقيرة وتدفع المستخدم لفتح شاشة منفصلة.

يجب أن تعرض البطاقة مباشرة:

```text
- رقم الطلب بوضوح.
- الحالة الحالية.
- الإجراء الآن.
- عداد وقت أو SLA.
- عناصر الطلب بشكل واضح ومفصل.
- الكمية أو عدد العناصر.
- المبلغ.
- طريقة الدفع.
- حالة الدفع عند توفرها.
- نمط التوصيل.
- الجهة التالية.
- حالة موصل المتجر أو كابتن بثواني حسب النمط.
- ملاحظات الطلب المهمة.
- جرس الطلب الجديد عند الحاجة للرد.
- أزرار الإجراء الأساسية.
- تفاصيل منسدلة داخل البطاقة، لا شاشة منفصلة.
```

---

### 0.3 الشريط السفلي والهيدر يجب أن يكونا في نفس ملف مالك الـ Surface/Shell

في كل تطبيق من التطبيقات الأربعة، يجب أن يكون الهيدر والشريط السفلي مملوكين من نفس ملف الـ Surface/Shell المعني، وليس من شاشة داخلية.

القاعدة:

```text
App Surface/Shell owns:
- Header
- Bottom navigation
- Route switching
- Safe-area/padding
- Shared sheets that belong to shell level

Screen owns:
- Screen content only
- No bottom nav
- No app-level header
- No global shell behavior
```

التطبيقات الأربعة المقصودة:

```text
dsh/frontend/app-client/
dsh/frontend/app-partner/
dsh/frontend/app-captain/
dsh/frontend/app-field/
```

كل تطبيق قد يملك أسماء تبويبات مختلفة في الشريط السفلي، لكن نفس المبدأ والأسلوب:

```text
Header + BottomNav في ملف الـ Surface/Shell نفسه
Screens لا تحتوي BottomNav
Screens لا تحتوي header عام إذا كان الهيدر عام للتطبيق
```

---

### 0.4 توصيل المتجر = Store Delivery وليس Captain Delivery

المصطلحات المعتمدة:

```text
توصيل المتجر = Store Delivery
موصل المتجر = Store Courier
وضع موصل المتجر داخل تطبيق الكابتن = Store Courier Mode
```

المصطلحات الممنوعة داخل هذا السياق:

```text
كابتن متجر
Captain mode لموصل المتجر
كابتن بثواني
تسوية كابتن
محفظة كابتن
إسناد كابتن منصة
```

التعريف:

```text
توصيل المتجر خدمة يديرها الشريك.
موصل المتجر تابع للشريك/المتجر.
يمكنه استخدام تطبيق الكابتن بواجهة وصلاحيات محدودة.
لا يدخل في شبكة كباتن بثواني.
لا يستقبل طلبات بثواني العامة.
لا يأخذ منطق تتبع وتسوية كابتن بثواني.
تظهر عملياته ومستحقاته داخل حساب الشريك.
```

## 1) السياسات المعتمدة لتوصيل المتجر

عند تفعيل وضع توصيل المتجر، يجب أن يختار الشريك سياسة واضحة. لا يجوز أن يكون منطق التوصيل مخفيًا أو مبهمًا.

### 1.1 السياسة الأولى: توصيل مجاني

```text
store_delivery_policy = free_delivery
```

المعنى:

```text
العميل لا يدفع رسوم توصيل.
المتجر يتحمل التوصيل كعرض/خدمة.
لا توجد مستحقات موصل محسوبة من النظام.
```

ما يظهر للشريك:

```text
التوصيل مجاني — لا توجد رسوم محصلة لهذا الطلب.
```

ما يظهر للعميل:

```text
توصيل مجاني بواسطة المتجر.
```

---

### 1.2 السياسة الثانية: توصيل برسوم + مستحق لكل طلب لموصل المتجر

```text
store_delivery_policy = courier_per_delivery_payout
```

المعنى:

```text
العميل يدفع رسوم التوصيل.
يتم احتساب مستحق موصل المتجر لكل طلب.
تظهر المستحقات داخل تطبيق الشريك.
لا تتحول إلى تسوية كابتن بثواني.
```

مثال:

```text
رسوم التوصيل: 500
مستحق موصل المتجر: 300
المتبقي للمتجر: 200
```

---

### 1.3 السياسة الثالثة: توصيل برسوم + الرسوم للمتجر والموصل راتب/اتفاق داخلي

```text
store_delivery_policy = store_retained_fee_salary_courier
```

المعنى:

```text
العميل يدفع رسوم التوصيل.
رسوم التوصيل تدخل للمتجر.
الموصل موظف راتب/اتفاق داخلي.
لا توجد محاسبة لكل طلب داخل النظام.
```

ما يظهر للشريك:

```text
رسوم التوصيل لصالح المتجر.
الموصل راتب/اتفاق داخلي.
لا توجد مستحقات لكل طلب.
```

---

### 1.4 الفصل الإلزامي بين التسعير والتعويض والتسوية

```text
Delivery Pricing = كم يدفع العميل؟
Courier Compensation = كيف يُحاسب موصل المتجر؟
Settlement Owner = لمن تُنسب الرسوم؟
```

لا تخلط بينها.

أمثلة:

```text
رسوم التوصيل حسب تسعيرة بثواني: 500

إذا السياسة free_delivery:
- العميل يدفع 0.
- المتجر يتحمل الخدمة.

إذا السياسة courier_per_delivery_payout:
- العميل يدفع 500.
- موصل المتجر يستحق مبلغًا ثابتًا أو نسبة.
- تظهر المستحقات داخل تطبيق الشريك.

إذا السياسة store_retained_fee_salary_courier:
- العميل يدفع 500.
- الرسوم للمتجر.
- الموصل راتب/اتفاق داخلي.
```

## 2) Store Courier Mode داخل تطبيق الكابتن

### 2.1 القرار

يستخدم تطبيق الكابتن كحاوية تقنية فقط، لكن بمنطق وصلاحيات منفصلة:

```text
app-captain supports:
1. bthwani_captain_mode
2. store_courier_mode
```

### 2.2 ما يظهر في Store Courier Mode

```text
- طلبات المتجر المسندة له.
- استلام من الفرع.
- بدأ التوصيل.
- تم التوصيل.
- تعذر التوصيل.
- ملاحظات أو إثبات اختياري.
- مستحقاتي من المتجر إذا السياسة تسمح.
```

### 2.3 ما لا يظهر في Store Courier Mode

```text
- طلبات بثواني العامة.
- محفظة كابتن بثواني.
- تسويات كابتن بثواني.
- إسناد منصة عام.
- تتبع كابتن كامل.
- قبول/رفض طلبات من شبكة بثواني العامة.
```

### 2.4 نطاق الصلاحية

موصل المتجر لا يرى إلا:

```text
- الشريك المرتبط به.
- الفروع المسموحة له.
- الطلبات المسندة له.
- العمليات المالية الداخلية المرتبطة بالشريك إذا مفعلة.
```

## 3) شاشة منح صلاحية موصل المتجر في تطبيق الشريك

يجب أن تكون شاشة الصلاحيات واضحة قبل الحفظ.

### 3.1 الحقول المطلوبة

```text
اسم موصل المتجر
رقم الجوال
الفروع المسموحة
حالة التفعيل
نطاق الصلاحية: موصل متجر فقط
```

### 3.2 سياسة التوصيل

```text
- توصيل مجاني
- توصيل برسوم + مستحق لكل طلب
- توصيل برسوم + الرسوم للمتجر والموصل راتب/اتفاق داخلي
```

### 3.3 مصدر التسعير

```text
- حسب تسعيرة بثواني
- سعر ثابت من المتجر
- حسب نطاق/منطقة من لوحة التحكم
```

### 3.4 سياسة مستحق الموصل عند الحاجة

```text
- مبلغ ثابت لكل توصيل
- نسبة من رسوم التوصيل
- لا توجد مستحقات لكل طلب
```

### 3.5 ملخص قبل الحفظ

يجب عرض ملخص نهائي:

```text
هذا المستخدم موصل متجر فقط.
لن يستقبل طلبات بثواني العامة.
لن يدخل في تسويات كابتن بثواني.
عملياته ومستحقاته مرتبطة بالشريك.
سياسة التوصيل المختارة: [السياسة]
مصدر التسعير: [المصدر]
نطاق الفروع: [الفروع]
```

## 4) حالات الطلب المعتمدة حسب نمط التوصيل

### 4.1 توصيل بثواني

توصيل بثواني يحتفظ بمنطق الكابتن الكامل:

```text
ready
captain_assigned
captain_arriving
handoff
delivering
completed
```

واجهة الشريك تعرضها بلغة مفهومة:

```text
جاهز لتسليم كابتن بثواني
تم تعيين كابتن بثواني
الكابتن في الطريق للفرع
تم تسليم الطلب للكابتن
في الطريق للعميل
تم التوصيل
```

---

### 4.2 توصيل المتجر

حالات توصيل المتجر:

```text
ready
assigned_to_store_courier
picked_up_by_store_courier
store_courier_delivering
delivered_by_store_courier
store_delivery_failed
```

واجهة الشريك تعرضها ببساطة:

```text
جاهز للتسليم
مع موصل المتجر
في الطريق للعميل
تم التوصيل
تعذر التوصيل
```

لا تعرض مسميات تقنية معقدة داخل البطاقة.

## 5) بطاقة الطلب النهائية المطلوبة

### 5.1 القاعدة

بطاقة الطلب يجب أن تكون أهم عنصر في الشاشة. يجب أن تكون واضحة ومفصلة وذكية بدون حاويات ثقيلة.

### 5.2 ممنوع

```text
- ممنوع عرض اسم العميل مطلقًا في بطاقة الطلب.
- ممنوع جعل البطاقة فقيرة وتحتاج شاشة منفصلة لفهم الطلب.
- ممنوع فتح شاشة تفاصيل منفصلة عند الضغط على التفاصيل.
- ممنوع حاوية خارجية كبيرة حول قائمة الطلبات.
- ممنوع تكرار badges.
- ممنوع استخدام space-between بطريقة تفصل الأيقونة عن النص في RTL.
- ممنوع hardcoded colors.
- ممنوع تصميم محلي قابل لإعادة الاستخدام خارج @bthwani/ui-kit.
```

### 5.3 ترتيب البطاقة

```text
ORD-4401                         يتبقى 6 دقائق
تحتاج قبول                       جرس طلب جديد

الإجراء الآن: قبول الطلب

3 عناصر:
- برغر كلاسيك × 1
- بطاطس كبيرة × 1
- مشروب غازي × 1

الدفع:
92 ر.ي · نقد عند التسليم

التوصيل:
توصيل المتجر · الجهة التالية: موصل المتجر
الحالة: جاهز للتسليم

ملاحظات:
بدون بصل · صوص إضافي

[قبول الطلب] [التفاصيل]
```

### 5.4 تفاصيل العناصر

يجب دعم عرض العناصر بهذه المستويات:

#### مستوى مختصر داخل البطاقة مباشرة

```text
3 عناصر: برغر كلاسيك، بطاطس كبيرة، مشروب غازي
```

#### مستوى مفصل داخل نفس البطاقة أو block منسدل

```text
- برغر كلاسيك × 1 — بدون بصل
- بطاطس كبيرة × 1 — صوص إضافي
- مشروب غازي × 1
```

لا تعتمد على اسم العميل لتفسير الطلب.

### 5.5 جرس الطلب

يظهر الجرس عندما:

```text
status in ['new', 'needs_accept'] && unread === true
```

الجرس يعني:

```text
طلب جديد يحتاج انتباه ورد سريع من الشريك.
```

عند فتح التفاصيل أو قبول الطلب أو معاينته:

```text
يتم اعتبار التنبيه ملاحظًا محليًا إذا لا يوجد backend.
```

### 5.6 التفاصيل المنسدلة

زر `التفاصيل` يفتح block داخل نفس البطاقة.

يحتوي:

```text
- العناصر بالتفصيل.
- الإضافات والاختيارات.
- ملاحظات الطلب.
- حالة الدفع.
- حالة التوصيل.
- سجل مختصر.
- سبب المشكلة إن وجد.
- أزرار مساعدة: مشكلة / تواصل / ملاحظة.
```

لا يفتح route منفصل.

## 6) الشريط السفلي والهيدر في التطبيقات الأربعة

### 6.1 القاعدة المعمارية

```text
Surface/Shell owns Header + BottomNav.
Screen owns content only.
```

### 6.2 التطبيق العميل

الملف المالك يجب أن يكون Surface/Shell الخاص بتطبيق العميل.

الشريط السفلي في العميل قد يحتوي تبويبات مثل:

```text
الرئيسية
البحث/الفئات
الخدمات
الطلبات
حسابي
```

لكن لا يتم فرض هذه الأسماء إذا كانت القائمة الحالية مختلفة. المطلوب هو نفس الآلية والتنظيم.

### 6.3 تطبيق الشريك

الملف المالك:

```text
dsh/frontend/app-partner/DshPartnerSurface.tsx
```

الشريط السفلي المقترح:

```text
حسابي
المحفظة
الطلبات
المخزون
العمليات
```

المهم:

```text
الطلبات launcher مركزي.
inbox/detail => orders active.
```

### 6.4 تطبيق الكابتن

الملف المالك يجب أن يكون Surface/Shell الخاص بتطبيق الكابتن.

يجب دعم:

```text
bthwani_captain_mode
store_courier_mode
```

أسماء التبويبات تختلف حسب الوضع.

مثال كابتن بثواني:

```text
الرئيسية
الطلبات
المحفظة
الدعم
حسابي
```

مثال موصل متجر:

```text
طلبات المتجر
التسليمات
مستحقاتي
الدعم
حسابي
```

### 6.5 التطبيق الميداني

الملف المالك يجب أن يكون Surface/Shell الخاص بتطبيق الميداني.

تبويباته حسب عمله:

```text
المهام
الفحص
الاعتمادات
الدعم
حسابي
```

### 6.6 ui-kit

إذا كانت آلية الشريط السفلي موجودة في `@bthwani/ui-kit`، تستخدم من public exports.

يجوز تعديل ui-kit فقط إذا:

```text
- النمط reusable فعلاً.
- الحاجة مثبتة عبر أكثر من تطبيق.
- التعديل صغير ومركزي.
- لا توجد إضافة ملفات جديدة إلا بموافقة.
```

## 7) إغلاق المظلة عبر الأسطح

لا يجوز إغلاق تطبيق الشريك وحده.

يجب تحليل وتعديل عند الحاجة:

```text
dsh/frontend/app-client/
dsh/frontend/app-partner/
dsh/frontend/app-captain/
dsh/frontend/app-field/
dsh/frontend/control-panel/
wlt/frontend/
contracts/types/shared models
@bthwani/ui-kit public exports
```

### 7.1 app-client

يجب أن يرى العميل:

```text
- حالة الطلب بلغة مفهومة.
- الفرق بين توصيل المتجر وتوصيل بثواني.
- عدم وجود تتبع كابتن بثواني عند توصيل المتجر.
- توضيح أن التوصيل بواسطة المتجر.
```

### 7.2 app-partner

يجب أن يرى الشريك:

```text
- بطاقة طلب كاملة بدون اسم العميل.
- كل تفاصيل الطلب المهمة.
- جرس الطلب الجديد.
- تفاصيل منسدلة.
- سياسة توصيل المتجر.
- موصل المتجر.
- المستحقات الداخلية عند الحاجة.
```

### 7.3 app-captain

يجب أن يدعم:

```text
- كابتن بثواني.
- موصل متجر بوضع محدود.
```

بدون خلط.

### 7.4 app-field

يفحص فقط ما له علاقة بـ:

```text
- اعتماد متجر.
- تفعيل خدمة توصيل المتجر.
- فحص موصلين أو وثائق إن وجدت.
- لا يضاف منطق غير لازم.
```

### 7.5 control-panel

يجب أن يدعم:

```text
- سياسة توصيل المتجر.
- مصدر التسعير.
- مراقبة طلبات توصيل المتجر.
- الطلبات المتأخرة.
- التعذر.
- التقارير.
- عدم خلطها بتسويات كابتن بثواني.
```

### 7.6 WLT

يجب أن يفرق بين:

```text
- رسوم توصيل بثواني.
- رسوم توصيل المتجر.
- مستحقات موصل المتجر الداخلية.
- تسوية الشريك.
- لا تسوية كابتن بثواني لموصل المتجر.
```
