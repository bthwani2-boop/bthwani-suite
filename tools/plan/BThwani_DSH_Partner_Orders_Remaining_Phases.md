# خطة تنفيذ مظلة DSH المتبقية — شاشة طلبات الشريك ومنطق توصيل المتجر

> الهدف: إغلاق منطق طلبات DSH كمنظومة واحدة متعددة الأسطح، وليس كتحسين معزول لتطبيق الشريك.
> المسار المحلي المعتمد: `C:\bthwani-suite`
> الريبو المعتمد: `bthwani2-boop/bthwani-suite`
> الفرع الذي يجب مراجعته محليًا قبل التنفيذ: الفرع الحالي المفتوح لدى المنفذ، مع مقارنة Git قبل APPLY.

---

## 1) الحكم التنفيذي الحالي

الحالة الحالية ليست مغلقة. تم تنفيذ أجزاء مهمة، لكن بقيت فجوات تشغيلية ومنطقية وتصميمية:

1. الشريط السفلي ظهر، لكن يجب تثبيته كجزء من `DshPartnerSurface` فقط، مع منع أي وجود له داخل `OrdersInboxScreen`.
2. بطاقة الطلب أصبحت تعرض تفاصيل أكثر، لكنها ما زالت ليست بطاقة تشغيل مناسبة لكاشير تحت ضغط.
3. اسم العميل ما زال حاضرًا بشكل غير مناسب في سياق تشغيل الكاشير، ويجب أن يصبح ثانويًا أو داخل التفاصيل فقط.
4. منطق جرس الطلب الجديد غير مغلق.
5. زر التفاصيل يجب ألا يفتح شاشة منفصلة؛ الأفضل تفاصيل منسدلة داخل نفس البطاقة أو Bottom Sheet خفيف حسب الحاجة.
6. تصميم “الحاوية الكبيرة حول الطلبات” يجب إلغاؤه؛ القائمة يجب أن تكون stream عمليًا مباشرًا.
7. منطق توصيل المتجر يجب تبسيطه وفصله عن منطق كابتن بثواني.
8. لا يوجد منع أعمى لتعديل أي سطح، لكن أي تعديل خارج `app-partner` يجب أن يكون مثبتًا بخريطة أثر مباشرة على DSH order lifecycle.

## 2) قرار توصيل المتجر المعتمد

### 2.1 القاعدة

```text
توصيل بثواني = شبكة كباتن + إسناد + تتبع + حالات كابتن + تسويات كابتن.
توصيل المتجر = مسؤولية المتجر + تأكيدات تشغيلية بسيطة + رقابة لوحة التحكم.
```

### 2.2 ممنوع في توصيل المتجر

لا تعامل موصل المتجر ككابتن بثواني. لا تضف له:

- تتبع حي للكابتن.
- إسناد كابتن من المنصة.
- قبول/رفض من كابتن.
- captain_assigned / captain_arriving بنفس معنى بثواني.
- تسويات كابتن.
- محفظة كابتن.
- availability للكابتن داخل منظومة بثواني.

### 2.3 الدورة المعتمدة لتوصيل المتجر

```text
needs_accept / new
→ accepted
→ preparing
→ ready
→ handed_to_store_courier
→ delivered_by_store
```

حالات الاستثناء:

```text
store_delivery_failed
store_delivery_returned
customer_unreachable
```

### 2.4 ماذا يرى الكاشير؟

عند `توصيل المتجر`:

```text
ORD-4401
الإجراء الآن: تسليم لموصل المتجر
3 عناصر: برغر كلاسيك، بطاطس، مشروب
توصيل المتجر · موصل المتجر
92 ر.ي · نقد عند التسليم
[سُلّم لموصل المتجر]
```

بعد التسليم لموصل المتجر:

```text
ORD-4401
الحالة: مع موصل المتجر
الإجراء الآن: تأكيد التوصيل
[تم التوصيل] [تعذر التوصيل]
```

### 2.5 ماذا يرى العميل؟

```text
المتجر يجهز طلبك
طلبك مع موصل المتجر
تم التوصيل
تعذر التوصيل — سيتم التواصل معك
```

مع توضيح:

```text
هذا الطلب يتم توصيله بواسطة المتجر.
```

### 2.6 ماذا ترى لوحة التحكم؟

لوحة التحكم لا تدير موصل المتجر كأسطول. تعرض فقط:

- عدد طلبات توصيل المتجر.
- طلبات جاهزة للتسليم لموصل المتجر.
- طلبات مع موصل المتجر ولم تؤكد.
- طلبات تم توصيلها.
- طلبات تعذر توصيلها.
- طلبات تجاوزت SLA أو لم تؤكد التسليم.

### 2.7 ماذا يحدث ماليًا؟

لا توجد تسوية كابتن. توجد فقط:

- حالة دفع الطلب.
- نقد عند التسليم إن وجد.
- المبلغ بعهدة المتجر إذا موصل المتجر يجمع النقد.
- تسوية شريك/متجر، لا تسوية كابتن.

## 3) خريطة المراحل المتبقية

### PHASE 0 — بوابة تشخيص محلية قبل أي APPLY

#### الهدف
منع أي تنفيذ مبني على الذاكرة أو على GitHub فقط؛ الصور قد تكون من تغييرات محلية غير مرفوعة.

#### يجب تنفيذ
```powershell
Set-Location -LiteralPath "C:\bthwani-suite"
git --no-pager status --short
git --no-pager diff -- dsh/frontend/app-partner/DshPartnerSurface.tsx
git --no-pager diff -- dsh/frontend/app-partner/screens/OrdersInboxScreen.tsx
git --no-pager diff -- ui-kit/src/components/navigation.tsx
```

#### يجب إثبات
- هل يوجد `BottomNavBar` داخل `OrdersInboxScreen`.
- أين يملك `DshPartnerSurface` الهيدر والشريط السفلي.
- هل `openOrdersBoard()` يغلق `searchMode` ويعيد `route='inbox'`.
- هل `inbox/detail` يجعلان زر الطلبات active.
- أين توجد الحاوية الكبيرة حول قائمة الطلبات.
- أين يظهر اسم العميل داخل بطاقة الطلب.
- أين يوجد زر التفاصيل الحالي وماذا يفعل.
- أين توجد حقول `itemsSummaryLabel`, `paymentLabel`, `slaLabel`, `nextOwnerLabel`.
- هل توجد حقول مناسبة لجرس الطلب الجديد أم لا.

---

### PHASE 1 — تثبيت Shell والهيدر والشريط السفلي

#### الهدف
استعادة/تثبيت الشريط السفلي منطقياً داخل نفس مالك الهيدر: `DshPartnerSurface`.

#### المطلوب
- `DshPartnerSurface` هو المالك الوحيد للهيدر والشريط.
- `OrdersInboxScreen` لا يحتوي أي BottomNav أو placeholder أو View debug.
- زر الطلبات المركزي:
  - `onLauncherPress => openOrdersBoard()`
  - `openOrdersBoard()` ينفذ:
    - `setOrdersSearchMode(false)`
    - `setRoute('inbox')`
- `route === 'inbox' || route === 'detail'` يجب أن يعامل كـ `orders active`.

#### إذا كان `BottomNavBar` لا يدعم `launcherActive`
يجوز تعديل `@bthwani/ui-kit` فقط إذا ثبت أنه reusable ومطلوب لأكثر من سطح. وإلا يسجل كـ Finding.

#### قبول المرحلة
- الشريط ظاهر في: `inbox`, `detail`, `home`, `inventory-management`, `support-directory`, `support-screen`.
- لا يوجد شريط داخل صفحات الطلبات.
- لا يوجد clipping فوق Android navigation bar.

---

### PHASE 2 — إزالة الحاوية الكبيرة وتحويل القائمة إلى stream

#### الهدف
إلغاء تصميم الحاويات الثقيلة حول الطلبات.

#### المطلوب
- إزالة الـ `Surface/Card/Box` الكبير الذي يلتف حول كل قائمة الطلبات.
- الهيكل الجديد:
```text
Search/filter command
Stage rail
Count مختصر
Orders stream مباشر
```
- كل طلب بطاقة مستقلة خفيفة.
- لا إطار خارجي ضخم حول كل الطلبات.
- الحفاظ على `paddingBottom` كافٍ للشريط السفلي.
- لا تكديس shadows/borders.

#### قبول المرحلة
- لا تظهر الحاوية الكبيرة المحددة سابقًا.
- الطلبات تبدو stream واضحًا.
- قائمة الطلبات تبدأ بسرعة بعد الفلاتر.

### PHASE 3 — بطاقة طلب كاشير حقيقية

#### الهدف
تحويل البطاقة إلى بطاقة تشغيل لحظية لا بطاقة CRM.

#### ترتيب البطاقة المعتمد

```text
ORD-4401                       يتبقى 6 دقائق
تحتاج قبول
الإجراء الآن: قبول الطلب
3 عناصر: برغر كلاسيك، بطاطس كبيرة، مشروب
توصيل المتجر · الجهة التالية: موصل المتجر
92 ر.ي · نقد عند التسليم
[قبول الطلب] [التفاصيل]
```

#### قواعد البطاقة
- رقم الطلب هو العنوان الأساسي.
- اسم العميل لا يكون عنوانًا.
- اسم العميل يظهر فقط:
  - مختصرًا جدًا كـ meta عند الضرورة، أو
  - داخل التفاصيل المنسدلة.
- الإجراء الآن يظهر قبل التفاصيل الثانوية.
- عناصر الطلب تظهر بوضوح.
- الدفع والتوصيل والجهة التالية ظاهرة.
- زر أساسي واحد فقط.
- زر ثانوي واحد للتفاصيل.
- لا تكرار لنفس badge.
- لا حاوية داخل حاوية.

#### حقول اختيارية مسموحة
```ts
customerShortLabel?: string;
itemsSummaryLabel?: string;
paymentLabel?: string;
paymentStatusLabel?: string;
fulfillmentOwnerLabel?: string;
slaLabel?: string;
nextOwnerLabel?: string;
cashierNoteLabel?: string;
```

#### قبول المرحلة
- الكاشير يعرف الإجراء خلال ثانيتين.
- البطاقة ليست طويلة أو مزدحمة.
- اسم العميل لا يسيطر بصريًا.

---

### PHASE 4 — جرس الطلب الجديد لكل طلب

#### الهدف
تنبيه الكاشير عند وصول طلب جديد يحتاج ردًا.

#### المنطق
```text
status in ['new', 'needs_accept'] && unread === true
=> show per-order bell indicator
```

#### المطلوب
- جرس واضح داخل بطاقة الطلب، ليس مجرد Chip نصي.
- يظهر فقط للطلبات الجديدة/المعلقة التي تحتاج انتباه.
- عند:
  - فتح تفاصيل الطلب،
  - قبول الطلب،
  - معاينة الطلب،
  يتم اعتبار التنبيه تمت ملاحظته محليًا إن لم يوجد backend.
- جرس الهيدر يبقى للإشعارات العامة.
- جرس البطاقة للتنبيه التشغيلي للطلب نفسه.

#### قبول المرحلة
- كل طلب جديد يحتاج قبول يظهر له جرس.
- لا يوجد خلط بين جرس الهيدر وجرس الطلب.
- لا يتحول الجرس إلى ضوضاء دائمة لكل البطاقات.

---

### PHASE 5 — التفاصيل المنسدلة بدل شاشة منفصلة

#### الهدف
عدم إخراج الكاشير من السياق عند الضغط على التفاصيل.

#### المطلوب
- زر `التفاصيل` يفتح inline expandable details block داخل نفس البطاقة.
- لا route جديد.
- لا شاشة منفصلة.
- يمكن استخدام Sheet خفيف فقط إذا كان inline block غير مناسب تقنيًا، ويجب إثبات السبب.

#### محتوى التفاصيل المنسدلة
- العميل مختصرًا أو كاملًا عند الحاجة.
- العناصر بتفصيل أكثر.
- إضافات/ملاحظات الطلب.
- حالة الدفع.
- حالة التوصيل.
- سجل مختصر:
  - وصل الطلب.
  - تم القبول.
  - بدأ التحضير.
  - جاهز.
  - سُلّم لموصل المتجر / كابتن بثواني.
- اختصارات:
  - رسالة سريعة.
  - مشكلة في الطلب.
  - تواصل عند الحاجة.

#### قبول المرحلة
- لا خروج من قائمة الطلبات.
- الفتح والإغلاق واضح.
- لا يسبب تمددًا مزعجًا للبطاقة.
- يحافظ على RTL.

---

### PHASE 6 — تبسيط منطق توصيل المتجر

#### الهدف
إغلاق منطق توصيل المتجر بدون تعقيد كابتن بثواني.

#### المطلوب في بطاقة الطلب
- `orderTypeLabel`: توصيل المتجر.
- `nextOwnerLabel`: موصل المتجر.
- delivery state:
  - جاهز للتسليم.
  - سُلّم لموصل المتجر.
  - تم التوصيل.
  - تعذر التوصيل.
- الإجراء التالي:
  - تسليم لموصل المتجر.
  - تأكيد التوصيل.
  - معالجة تعذر التوصيل.

#### ممنوع
- لا captain tracking.
- لا captain settlement.
- لا captain wallet.
- لا captain availability.
- لا captain arriving لموصل المتجر.

#### قبول المرحلة
- الفرق بين توصيل المتجر وتوصيل بثواني واضح.
- لا يوجد منطق كابتن في توصيل المتجر.
- العميل ولوحة التحكم يحصلان على حالة واضحة.

---

### PHASE 7 — إغلاق المظلة عبر الأسطح

#### الهدف
عدم ترك الشريك منفصلًا عن بقية DSH.

#### يجب فحص/تعديل عند الحاجة
- `app-client`: حالات الطلب المرئية للعميل.
- `app-captain`: حالات توصيل بثواني فقط.
- `app-field`: أي فحص/اعتماد/توثيق مرتبط بالطلبات.
- `control-panel`: العمليات، SLA، التدقيق، مشاكل الشريك، توصيل المتجر.
- `wlt`: الدفع، COD، المحفظة، مستحقات الشريك.
- shared contracts/types إن وجدت.

#### يجوز التعديل إذا ثبت
- تسمية حالة متناقضة.
- حالة تظهر في الشريك ولا تستطيع لوحة التحكم تتبعها.
- توصيل المتجر مختلط مع كابتن بثواني.
- WLT يعرض أثرًا ماليًا خاطئًا.
- contract مكرر يخلق divergence.

#### لا يجوز التعديل إذا كان
- تحسينًا تجميليًا عامًا.
- إعادة تصميم غير مرتبطة.
- تعديلًا واسعًا بدون خريطة أثر.

# أمر التنفيذ الدقيق — المرحلة التالية

انسخ الأمر التالي إلى VS Code Copilot Chat:

```text
يجب قبل التنفيذ الاطلاع على ملفات الوكلاء والـ skills ذات العلاقة وتطبيق ما يخص المهمة منها بدقة، وعدم الاعتماد على الذاكرة أو الافتراض.

نفّذ المراحل التالية لشاشة طلبات تطبيق الشريك DSH وفق المظلة: BThwani منظومة واحدة متعددة الأسطح وليست تطبيقات منفصلة.

المطلوب الآن:
PHASE 0 + PHASE 1 + PHASE 2 فقط:
- تشخيص محلي قبل APPLY.
- تثبيت Shell والهيدر والشريط السفلي.
- إزالة الحاوية الكبيرة حول قائمة الطلبات وتحويل القائمة إلى stream عملي مباشر.

لا تنتقل إلى PHASE 3 إلا بعد أن تكتب DONE/BLOCKED للمراحل الثلاث الأولى مع الأدلة.

السياق:
- الشريط السفلي ظهر بصريًا لكنه يجب أن يبقى مملوكًا من DshPartnerSurface فقط.
- OrdersInboxScreen يجب ألا يحتوي BottomNav ولا debug placeholder.
- زر الطلبات يجب أن يعيد إلى inbox ويغلق search/filter transient state.
- القائمة الحالية ما زالت محاطة بحاوية كبيرة وغير مناسبة.
- تصميم الحاويات الثقيلة مرفوض.
- توصيل المتجر يجب أن يبقى بسيطًا ولا يأخذ منطق كابتن بثواني.

النطاق الأساسي:
- dsh/frontend/app-partner/DshPartnerSurface.tsx
- dsh/frontend/app-partner/screens/OrdersInboxScreen.tsx

النطاق المشروط:
يجوز تعديل @bthwani/ui-kit فقط إذا ثبت أن BottomNavBar يحتاج prop reusable مثل launcherActive ولا يمكن إغلاق active state بدون تعديل مركزي صغير. لا تنشئ ملفات ui-kit جديدة إلا بعد BLOCKED وموافقة.

يجوز فحص وتعديل أي سطح آخر فقط إذا ثبت قبل APPLY أنه مرتبط مباشرة بكسر منطق DSH order lifecycle. لا يوجد منع أعمى، لكن لا يوجد تعديل عشوائي.

الممنوع:
- لا rename.
- لا حذف ملفات.
- لا routes جديدة.
- لا hardcoded colors.
- لا design system محلي.
- لا استيراد Tamagui مباشرة داخل screens/surfaces/apps.
- لا تعديل تجميلي خارج خريطة الأثر.
- لا تستخدم أو تذكر أي مسار/ريبو قديم باسم bth؛ الريبو الحالي والمعتمد فقط هو C:\bthwani-suite.
```
