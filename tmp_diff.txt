+## Core Rules
+
+### Screenshots
+
+- screenshots must be real captures from a simulator, physical device, or browser.
+- do not add fabricated, placeholder, or AI-generated images.
+- each screenshot filename must match the `screenshot_path` value in the ledger exactly.
+- use a new filename for each revision; do not overwrite old screenshots.
+
+### PASS
+
+- requires an actual `screenshot_path`.
+- requires a human reviewer name and `reviewed_at`.
+- cannot be self-reported by the engineer who wired the screen.
+
+### FAIL
+
+- requires `issue_type`, `issue_summary`, and `next_action` in the ledger row.
+- requires a corresponding entry in the failure tracking section below.
+
+### BLOCKED
+
+- requires a blocker reason in `issue_summary`.
+- `next_action` must describe what removes the block.
+
+### NOT_REVIEWED
+
+- initial state of every row in the ledger.
+- no result claim may be made from a `NOT_REVIEWED` row.
+
+---
+
+## Allowed `result` values
+
+| Value | Meaning |
+|---|---|
+| `NOT_REVIEWED` | No human review performed yet |
+| `PASS` | Reviewed and confirmed on device or browser |
+| `FAIL` | Reviewed and a visual defect was found |
+| `BLOCKED` | Cannot be reviewed because of environment or contract block |
+| `DEFERRED` | Intentionally deferred to a later review cycle |

+## Master Update Protocol
+
+Use this section as the standard process for any future visual review update.
+All updates happen inside this file.
+
+### Step 1 — Confirm the master file exists
+
+- Confirm `dsh/docs/DSH_VISUAL_REVIEW.md` exists.
+- Confirm the `review_id` exists in the embedded ledger table below.
+- Confirm the `screenshot_path` is not empty if `result` is `PASS` or `FAIL`.
+- Confirm the screenshot file exists on disk if `result` is `PASS` or `FAIL`.
+- If the screenshot file is missing, do not mark `PASS` or `FAIL`. Mark `BLOCKED` and explain `SCREENSHOT_FILE_MISSING`.
+- Do not create fake screenshot files.
+- Do not overwrite previous screenshot references. If this is a revision, add a new screenshot filename and update the ledger row to point to the latest one.
+
+### Step 2 — Update the ledger row
+
+Update the row for the reviewed screen in the ledger section below.
+
+Required updates:
+- `screenshot_path`
+- `result` (`PASS`, `FAIL`, `BLOCKED`, or `DEFERRED`)
+- `issue_type` (required if `FAIL`)
+- `issue_summary` (required if `FAIL` or `BLOCKED`)
+- `reviewer`
+- `reviewed_at`
+- `next_action`
+- `review_doc_path`
+
+Do not change these row values:
+- `review_id`
+- `screen_id`
+- `surface`
+- `file_path`
+- `queue_list`
+- `priority`
+
+### Step 3 — Create or update per-screen review notes
+
+The per-screen review document path remains the canonical review note location in the ledger row.
+If `review_doc_path` references a markdown file, create or update that file accordingly.
+
+Each review note must include at minimum:
+- `review_id`
+- `screen_id`
+- `surface`
+- `result`
+- `reviewer`
+- `reviewed_at`
+- screenshot path
+- notes on what was checked
+- visual diagnosis
+- RTL diagnosis
+- overflow / clipping diagnosis
+- CTA diagnosis
+- state coverage diagnosis
+- design system compliance notes
+- issue summary
+- next action
+- final screen status
+
+Final screen status must be one of:
+- `HUMAN_VISUAL_REVIEW_CONFIRMED`
+- `HUMAN_VISUAL_REVIEW_FAILED`
+- `HUMAN_VISUAL_REVIEW_BLOCKED`
+- `HUMAN_VISUAL_REVIEW_DEFERRED`
+
+### Step 4 — Update summary counts
+
+Update the status summary and metadata inside this file as needed.
+The ledger remains the authoritative row-level source.
+
+### Step 5 — Record failures
+
+If `result = FAIL`, add or update a failure entry in the failure tracking section below.
+If a result changes from `FAIL` to `PASS`, mark the existing failure entry as `RESOLVED`; do not delete it.
+
+### Step 6 — Record signoff
+
+If a screen passes review, add or update a signoff row in the signoff section below.
+Do not mark a screen confirmed without a real screenshot.
+
+### Step 7 — Update the screen index
+
+Update the screen index section only to reflect the latest `result` status.
+Do not change queue classification or review priority in the index.
+
